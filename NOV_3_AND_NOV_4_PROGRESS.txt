1. PROJECT STRATEGY AND SCOPE
=============================

The project is being positioned as an AI-powered hostel operations app with
PayPal Sandbox rent collection. The priority is one understandable transaction
loop:

  identify overdue rent
  -> prepare a tenant-specific collection request
  -> owner approves by requesting a PayPal order
  -> tenant completes or cancels Sandbox checkout
  -> server checks the PayPal result
  -> owner syncs the result
  -> app records a payment only after PayPal says COMPLETED

Money movement is approval-gated. The AI/model does not create, capture, or
record payments. The owner initiates an order, the tenant authorizes checkout
with PayPal, and PayPal is the status authority.

Payouts, subscriptions, dynamic pricing, and automatic tenant messaging remain
out of this critical path.

3. SNAPSHOT CONTRACT AND RENT CALCULATION
=========================================

Created src/agent/snapshot.ts and a focused snapshot test.

The snapshot contains:

- hostelName
- asOf date
- currency (USD)
- one row per active tenant, including tenantId, fullName, floor, room,
  monthlyRent, outstandingAmount, monthsOverdue, and recentMonths
- each recent month includes rentDue, amountPaid, outstandingAmount, and a
  paid/partial/unpaid status

The snapshot is built from the app's local tenant and payment records and
existing rent calculation helpers. The test verifies:

- Daniel: $700 outstanding, 2 months overdue, with paid/partial/unpaid month
  statuses.
- Mina: $380 outstanding, 1 month overdue.
- Leo: $0 outstanding, 0 months overdue.

monthsOverdue counts months with a positive unpaid balance as the existing
rent calculator reports it. The snapshot's recentMonths currently includes
up to the latest three calendar months.


4. AGENT AUTHORITY AND MODEL SETUP

- use only facts in the provided snapshot;
- do not invent why a tenant is late;

- exclude tenants with zero outstanding rent;

5. SERVER-SIDE PAYPAL RENT ORDER WORK
=====================================

Added server/paypal.js:

- obtains and caches a PayPal OAuth token using server-side credentials;
- uses the Sandbox API base by default;
- wraps PayPal API requests and request IDs;
- keeps the PayPal client secret on the server.

Added server/rent-orders.js:

- validates tenant snapshot fields and monthly rows;
- derives the collection amount by summing rentDue minus amountPaid for the
  supplied months, floored at zero per month;
- rejects a mismatch between the derived amount and outstandingAmount, and
  applies a $5,000 demo cap;
- creates USD PayPal orders with tenant/month allocation metadata;
- reuses an open order for the same tenant while the server is running;
- syncs an order against PayPal, captures an APPROVED order on the server, and
  validates the capture amount and currency;
- can recover order metadata from PayPal after server memory is lost, because
  tenant ID, amount, and month allocations are attached to the PayPal order.

IMPORTANT DATA TRUST LIMITATION:
The server checks the arithmetic in the snapshot sent by the browser. At this
stage, the server does not independently read the hostel's authoritative tenant
and payment records from Firebase before creating an order. Therefore, the
snapshot-mismatch test proves that changing only outstandingAmount to $1 is
rejected, but it does not make arbitrary client-supplied rent/payment rows
authoritative. Keep this demo restricted to the configured owner and Sandbox.
For production, the backend must fetch or otherwise verify trusted rent data.


6. OWNER AUTHENTICATION AND FRONTEND
====================================

Added server/owner-auth.js using Firebase Admin ID-token verification. The
backend checks the Firebase UID against OWNER_UID and the Firebase project
against FIREBASE_PROJECT_ID.

The PWA gets a Firebase ID token from the currently signed-in account and sends
it as a Bearer token for owner actions. This replaced the proposed
VITE_OWNER_ACTION_SECRET approach. A VITE_ value is included in browser code
and is not a secret. If VITE_OWNER_ACTION_SECRET was put in an env file, remove
it; rotate it if the same value was reused as a real server secret.

Added src/agent/rentOrders.ts for frontend request/sync calls. The backend URL
comes from VITE_API_BASE_URL and defaults locally to http://localhost:3000.
The frontend .env.example now includes that local API URL.

The dashboard now shows a Request $... from [tenant] button beside overdue
tenants. The button is disabled when no signed-in Firebase owner is present.
The returned PayPal approval link is displayed and is not automatically opened.
The owner may open it in a second browser profile for the Sandbox buyer.

The owner dashboard also displays the order status and a Sync with PayPal
button. On COMPLETED only, it records the PayPal capture locally. Payment rows
are allocated to the actual outstanding months, with stable IDs based on
capture ID plus month, to prevent duplicate local records when Sync is repeated.
Non-COMPLETED states do not create payment rows.


7. RETURN AND CANCELLATION REDIRECT
==================================

PayPal's return and cancel URLs point to the backend:

- /api/paypal/return checks/syncs the order with PayPal, then redirects to the
  PWA dashboard with a result marker.
- /api/paypal/cancel records the cancellation in the server's in-memory order
  cache when available, then redirects to the PWA dashboard.

The PWA removes the result query parameters and displays a toast:

- completed: PayPal confirmed payment; Sync the owner dashboard to record it.
- pending: PayPal did not confirm payment; no payment was recorded.
- cancelled: checkout was cancelled; no payment was recorded.

The user confirmed that cancellation now redirects back to the app. A screenshot
showed the toast "PayPal checkout cancelled. No payment was recorded." and the
seeded balance remained $1,080.

The cancellation order card still showed PAYER_ACTION_REQUIRED in the screenshot
after redirect, even though the toast and unchanged balance indicated that no
payment was recorded. This order-status display should be checked with Sync and
may need a UI/status-state follow-up. The cancellation redirect itself works.

13. FOLLOW-UP POLISH AND FIREBASE SYNC REPAIR
=============================================

The later verification exposed one outstanding Firebase queue error:
"Multiple cloud rooms have the same floor and room labels." This is a legacy
Firestore data conflict, unrelated to Gemini or PayPal. Duplicate cloud room
documents are retained; no data is deleted.

Fix:
- Tenant synchronization now chooses one matching active cloud room
  deterministically: highest capacity first, then stable document ID.
- Duplicate document IDs and the chosen canonical ID are logged with a
  warning; duplicate records are not automatically merged or deleted.
- Previously failed tenant queue entries with this exact duplicate-room error
  are automatically made retryable when sync runs again.
- Permission-denied failures now retain the sync phase (room lookup, occupant
  read, tenant/room transaction, or record write) and error code in Settings,
  replacing the previous overly generic message. This is intended to identify
  the remaining Firestore rule mismatch if a retry still fails.
- When synchronizing legacy tenant data, sync now preserves cloud `createdAt`
  and existing non-empty `rentHistory` if older local data omits them, and
  drops an empty `rentHistory` array that Firestore rules reject. It does not
  alter a non-empty local rent history or invent financial history.
- README documents the non-destructive behavior and recommends separately
  cleaning duplicate room records in Firestore when convenient.

The first retry after canonical-room selection showed a generic Firestore
rejection for the tenant transaction and its dependent payment. The deployed
rules file contained an unsupported `String.substring` call in the initial
rent-history check. Firebase CLI emitted an invalid-function warning while
compiling the old file; after replacing it with supported `split` comparisons,
the rules deployed cleanly. The owner retried the tenant and reported that
both the tenant and payment failures cleared.

Also polished the demo UX:
- PayPal return with `paypal=cancelled` now marks the matching saved order
  CANCELLED locally, hides its stale approval link, and retains cancellation
  when a later PayPal status refresh still reports an open order. A successful
  COMPLETED result still wins and is recorded as before.
- Rent Agent source labels now distinguish Gemini, rules fallback due to
  Gemini unavailability, and rules-only no-overdue results.
- README now states: “Agent proposes; owner requests; PayPal captures; the app
  records only after PayPal confirms COMPLETED.”

Added tests for deterministic duplicate-room selection, retrying existing
duplicate-room failures, preserving legacy tenant history/creation metadata,
and retaining cancellation when PayPal still reports an open order. The
updated frontend suite (27 tests), backend suite (9 tests), and production
build pass. Firebase CLI successfully compiled and deployed the corrected
rules. The Firestore emulator test suite was not run because Java is not
installed in this environment.

The reported live sync failure is resolved. The duplicate room documents
remain in Firestore; syncing uses the selected canonical active document and
does not delete the others. They can be cleaned up separately after confirming
which room record should remain authoritative.

Payment-specific follow-up (Nov 4):
